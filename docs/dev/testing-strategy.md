# 本地版自动化测试规范

> **最后更新日期**：2026-08-05  
> **状态**：执行中  
> **适用范围**：雪风AI短剧工坊开源单机版

## 一、定位与结论

本项目是面向个人创作者的单机应用：Next.js 运行在用户本机，SQLite 保存创作状态，图片、视频和成片写入本地目录；DeepSeek、Seedream、Seedance 等能力通过外部 API 调用。

测试目标不是复制在线版的完整平台测试体系，而是用较低维护成本保护本地版最容易造成实际损失的路径：

- 本地项目、剧本、素材、分镜和剪辑草稿不能因代码修改而丢失或串乱。
- 本地媒体只能在 `data/media` 内读写，不能发生目录穿越或错误覆盖。
- 模型、画幅、时长和视觉风格等生成参数必须保持有效且向后兼容。
- AI 服务失败、返回异常或未配置密钥时，应用应给出可理解的错误，不能写入半成品状态。
- 默认测试必须快速、可重复、无网络、无真实 API 费用，并且绝不接触用户现有的 `data` 目录。

因此，本项目采用“快速单元测试为主、少量 SQLite/API 集成测试补关键链路、发布前人工冒烟”的轻量策略，不要求建设在线 SaaS 所需的全套测试基础设施。

## 二、测试范围取舍

| 层级 | 本项目要求 | 说明 |
| --- | --- | --- |
| 静态检查与构建 | 必须 | TypeScript、ESLint 和 Next.js 构建负责发现类型、依赖和服务端/客户端边界问题。 |
| 单元与边界测试 | 必须 | 使用 Vitest，覆盖纯逻辑、输入约束、Skill 加载和本地文件安全。 |
| SQLite 集成测试 | 少量、按风险补充 | 只覆盖初始化、级联删除、关键状态流转和保存恢复；使用临时目录中的真实 SQLite。 |
| API 路由测试 | 关键路由按需补充 | 外部 AI 和下载请求统一 mock，验证参数校验、错误转换与本地持久化。 |
| 浏览器 E2E | 当前不作为门禁 | 页面结构稳定后，只考虑补一条核心创作链路；不追求全页面覆盖。 |
| 真实 AI 调用 | 不进入自动测试 | 会联网、产生费用且结果不确定，只允许维护者在发布前按需人工验证。 |
| 性能与并发测试 | 默认不建设 | 单用户本地应用没有在线平台的高并发、分布式一致性和容量风险。 |

### 明确不照搬在线版的测试

以下能力不属于本项目定位，除非产品边界发生变化，否则不建设对应自动化测试：

- 多用户登录、角色权限、租户隔离和资源归属。
- 积分、订阅、支付、退款、发票及计费幂等。
- MySQL、Prisma、Redis、OSS、任务队列和分布式 Worker。
- 高并发、压力测试、故障转移和多实例数据一致性。
- 大规模浏览器矩阵、移动设备矩阵和逐页面视觉快照。
- 真实 AI 模型的固定输出断言或在 CI 中使用真实密钥。
- 为追求覆盖率数字而测试无业务分支的展示代码。

## 三、必须保护的测试边界

### 3.1 配置与纯逻辑

这类测试是默认测试集的主体，修改相关代码时必须同步更新：

- 项目题材、画幅、视觉风格的默认值、归一化与生成提示词。
- 图片和视频模型 ID、画幅到分辨率的映射、4–15 秒时长约束。
- 剧集、分镜、素材和剪辑数据的解析、排序、默认值及状态转换。
- AI 请求参数拼装和响应解析；同类分支优先使用表格驱动测试。
- 修复过的纯逻辑缺陷必须增加能够复现原问题的回归用例。

### 3.2 Skill 与提示词资源

- Skill frontmatter、名称和引用资料必须可以稳定加载。
- Skill 直接引用的专业资料需要验证会被预加载，避免部署后缺少上下文。
- 禁止绝对路径、`..` 路径穿越和非标准 Skill 名称。
- 测试关注结构、必要约束和引用关系，不对整段提示词做易碎的全文快照。
- 优化提示词时应验证用户的题材、角色、时代、集数等明确要求不会被擅自删除。

### 3.3 本地媒体与文件安全

- Base64 data URL 的格式、MIME、空内容和 30MB 上限。
- 中文、空格和特殊字符路径的 URL 编码。
- `data/media` 目录穿越、绝对路径和混合路径分隔符。
- 文件下载失败、空文件、超限文件和临时文件写入失败。
- Range 请求的起止边界及不存在文件的错误响应。
- 图片或视频落盘应先写临时文件再原子重命名；失败不能留下被当作成品读取的文件。

### 3.4 SQLite 本地数据

数据库测试只覆盖数据安全相关行为，不穷举每个 getter/setter：

- 空数据目录首次启动能够创建数据库和全部表。
- 项目创建、更新、关闭数据库后重新打开，数据仍能正确恢复。
- 删除项目时，其剧集、素材、素材版本、分镜、视频版本和剪辑草稿正确级联删除。
- 同一项目的剧集序号、同一剧集的分镜序号保持唯一。
- 替换剧本或分镜时，任一步骤失败不能留下明显的半成品数据。
- 视频任务从 `pending`、`generating` 到 `success`/`failed` 的状态和所选版本保持一致。
- 相同供应商任务结果被重复查询时，不重复创建视频版本。
- JSON 字段损坏时使用安全默认值，不导致整个项目列表无法打开。

所有 SQLite 测试必须把 `DATA_DIR` 指向测试进程创建的临时目录，并在测试结束后关闭 `global.__shortDramaDb`、删除临时目录。禁止读取、复制、修改或删除仓库真实的 `data/studio.sqlite` 和 `data/media`。

### 3.5 API 与外部服务边界

优先测试包含数据写入或任务状态变化的路由：项目、剧本、素材、分镜、视频任务和剪辑草稿。测试至少覆盖：

- 请求体缺失、字段类型错误、非法模型/时长/分辨率以及资源不存在。
- 未配置 `DEEPSEEK_API_KEY` 或 `VOLCENGINE_API_KEY` 时返回明确错误。
- AI 服务非 2xx、超时、无效 JSON、缺少必要字段时，不把项目标记为成功。
- DeepSeek、Seedream 和 Seedance 的 `fetch` 必须 mock；断言请求结构和响应转换，不断言模型文案完全一致。
- 图片 Base64 和临时视频 URL 的模拟结果必须落到临时 `DATA_DIR`，页面数据只保留本地媒体路径。
- Seedance 查询接口重复返回同一任务结果时保持幂等。
- FFmpeg 自动测试只验证参数构造和错误处理；真实编码使用小型 fixture 或发布前人工冒烟，不提交大型媒体文件。

## 四、核心创作链路

本地版不需要为每个按钮建设 E2E。新增集成测试时，优先保护一条不调用真实 AI 的最小工作流：

```text
建立片场
  → 保存剧本与剧集
  → 创建角色/场景/道具和图片版本
  → 生成或编辑分镜
  → 保存视频任务及视频版本
  → 保存剪辑草稿
  → 关闭并重新打开数据库后完整恢复
```

这条链路可以在数据库/API 层完成，不强制引入 Playwright。只有出现多次“接口正确但页面流程不可用”的回归后，才引入一条浏览器级冒烟测试，并继续使用模拟 AI 响应。

## 五、运行门禁

### 5.1 日常开发

修改业务逻辑后至少运行：

```bash
npm run typecheck
npm test
```

仅修改文档、截图或不参与构建的静态资源时，可以不运行测试，但提交说明中应明确“仅文档/资源变更”。

### 5.2 提交或发布前

涉及 TypeScript、依赖、配置、页面或 API 的提交，以及正式版本发布前，运行完整本地门禁：

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

任一命令失败都不应发布。该门禁可以由维护者本地执行；当前项目不强制建立数据库服务、浏览器农场或复杂 CI。以后若增加 GitHub Actions，也只需执行上述四项，不引入真实 AI 密钥。

### 5.3 发布前人工冒烟

正式版本至少人工确认：

1. 使用全新的临时 `DATA_DIR` 启动应用并建立片场。
2. 刷新或重启应用后，项目和创作进度仍然存在。
3. 能编辑剧本、素材、分镜和剪辑草稿，删除操作只影响目标数据。
4. 未配置 API 密钥时提示清楚，页面不会卡在永久加载状态。
5. 有测试密钥且本次修改涉及模型适配时，各调用一次受影响的 AI 能力，并核对结果已保存到本地。
6. 修改媒体或剪辑功能时，用一个短小样例验证媒体预览、Range 播放和成片输出。

第 5、6 项按改动范围执行，不要求每次发布都消耗全部模型费用或重新编码完整短剧。

## 六、测试文件与数据规范

- 测试框架统一使用 Vitest，默认运行环境为 Node。
- 测试文件与被测模块相邻，命名为 `*.test.ts`；真实临时 SQLite 测试命名为 `*.integration.test.ts`。
- fixture 只保存能复现行为的最小文本、JSON、图片或视频，不提交密钥、真实用户数据、完整剧本和大媒体文件。
- 测试不得依赖执行顺序、当前工作目录之外的私人文件、开发者已有数据库或公网可用性。
- 时间、UUID、随机数和 `fetch` 在会影响断言时应固定或 mock。
- 每个测试负责清理自己创建的临时数据库、媒体文件、环境变量和全局数据库实例。
- 断言结果和可观察行为，不绑定内部实现；避免对大对象、完整提示词和页面 DOM 建立易碎快照。
- 测试标题使用中文或清晰英文描述业务结论，失败信息应能直接指出哪个用户行为被破坏。

## 七、覆盖率与新增测试规则

本项目暂不设置全仓覆盖率硬阈值。是否补测试按风险判断：

必须补测试的情况：

- 修复数据丢失、路径安全、状态错乱、参数失效或重复生成问题。
- 修改数据库表结构、级联关系、媒体保存、任务轮询或模型响应解析。
- 新增包含多分支的纯逻辑，或新增会写入本地数据的 API。
- 修改 Skill 加载、提示词引用规则或模型能力约束。

通常不要求补测试的情况：

- 纯文案、README、截图和视觉间距调整。
- 没有业务逻辑的简单展示组件。
- 第三方组件库已经覆盖、且本项目没有增加额外分支的行为。

覆盖率只用于发现关键模块盲区，不作为制造低价值测试的目标。评审测试时优先问“这个用例能否阻止用户数据丢失或核心创作流程回归”，而不是只看百分比。

## 八、当前基线与后续顺序

当前已有 Vitest 测试覆盖项目配置、模型约束、Base64 解析、本地媒体路径、Skill 加载和目录穿越防护。

后续按以下顺序补齐即可，无需一次性扩成在线版规模：

1. SQLite 临时目录初始化、保存恢复和级联删除测试。
2. 视频任务重复查询、成功/失败状态流转测试。
3. AI Provider 的请求与异常响应测试，全部 mock 网络。
4. 一条数据库/API 层核心创作链路测试。
5. 只有真实回归证明必要时，再增加单条浏览器 E2E。

以上完成后，本项目即可形成与单机定位相匹配的自动化保护；多租户、计费、分布式和高并发测试继续由在线版承担。
